> 生成时间：2026-09-12　生成脚本：`技能知识库/generate_skill_docs.py`（可复跑）

## 一、这批文件是什么

| 项目 | 内容 |
|---|---|
| 文档数 | **60 篇**（8 个人才维度下共 60 个技能，一个技能一篇） |
| 每篇构成 | 同一技能的 **5 张能力等级卡片**（L1—L5）聚合，另含技能 ID、所属领域、技能定义、评分区间 |
| 数据源 | `ai-career-dataset/data/v1.0-full`（该版本引用完整性 **200/200**，是唯一自洽的版本） |
| 篇幅 | 646—690 字（中位 657），**全部 ≤800 字** |
| 换行 | LF（已规避 Windows CRLF 导致平台字符计数翻倍的问题） |

**为什么是一个技能一篇，而不是一张卡片一片？**
依据 [`卡片组织方案对比/五类query完整对比.md`](卡片组织方案对比/五类query完整对比.md) 的实测：300 张 `skill_level` 卡片中，**同一技能的 L1 与 L2 去掉数字后文字完全相同，L3 与 L4 也完全相同**（60 个技能全部如此，5 个等级实际只承载 3 种信息）。拆成 300 片会让 Top5 被同一技能的不同等级占满，正确切片与干扰切片的分数窗口只有 **0.05**；聚合后窗口扩大到 **0.35**，可被阈值干净地切分。

## 二、上传操作步骤

### 1. 创建知识库

访问 [b.tbox.cn/inc/knowledge](https://b.tbox.cn/inc/knowledge) → 创建知识库 → 类型选 **文档型知识库**
（平台约束：文档型知识库仅支持关联**非结构化数据**，支持 1 对 N，可多文件关联）

### 2. 上传数据

**上传 `技能知识库/` 目录下的 60 个 `.md` 文件**（一次多选拖入）。
⚠️ 只上传那 60 个 `.md`，不要上传 `上传清单.csv`、`生成统计.json`、`generate_skill_docs.py`、`make_hit_test_table.py`。

### 3. 分段策略 —— 这一步最关键，配错整批就白做

| 参数 | 设定值 | 理由 |
|---|---|---|
| 分段策略 | **自定义分段策略** | 智能分段会按标题把一篇切成 5 段，聚合效果归零 |
| **分段最大限制** | **800**（务必改，默认是 500） | 默认 500 会让每篇 646—690 字的文档被切成 2 段。平台允许 300—8000，设 800 即可让整篇落入**单个分段** |
| 分段标识符 | 中文句号 | 语义上最合理的断点 |
| 上下文重叠长度 | **0** | 一篇即一段，重叠无意义，反而会制造同篇内的重复内容 |

**为什么必须让「一篇 = 一个分段」：** 聚合方案的收益就在于让模型一次看到 L1→L5 的完整梯度，从而能回答「这个技能学到什么程度算够用」这类真实提问。如果被切回 5 段，就退化回 300 片方案，等于没做聚合。

> ✅ **上传后必查**：在「数据仓库」列表查看每篇的**分段数量**，应为 **1**。
> 若显示 5，说明平台按 Markdown 标题切分了 → 打开「分段视图」，手动合并，或把分段标识符改为自定义（如 `## `）。分段视图支持**编辑与删除分段**，也可改用**手动分段**。这一步不做，方案设计就落空了。

### 4. 总结策略（可选，建议第二轮再开）

平台支持 **分段智能总结** 与 **分段问题生成** 两种策略，可同时开启，官方说明能「提升知识召回的精准度与匹配度」。
**第一轮先不开**——保持基线纯净，否则后面无法判断效果提升来自分段策略还是来自 AI 总结。

### 5. 自定义数据属性（支撑精确筛选与合规答辩）

平台内置属性只有 `doc_id`、`doc_name`、`gmt_create`；其余需自定义。建议按**英文名**建三个（团队文档要求字段名英文）：

| 属性名 | 类型 | 取值示例 | 用途 |
|---|---|---|---|
| `skill_id` | STRING | `SKILL-001` | 精确锁定单个技能文档 |
| `dimension` | STRING | `编程与计算基础` | 按 8 个维度筛选 |
| `claim_level` | STRING | `primary_derived` | 只检索已核验数据，AI 伦理要求「数据可溯源」 |

取值对照见 `技能知识库/上传清单.csv`（文件名 → 各属性值一一对应）。
> 属性值的录入入口在平台侧，本文档未查到批量导入方式，需在平台逐篇配置或询问平台客服。

## 三、检索参数建议（对齐评测集）

`retrieval_eval` 的验收规则是「`expected_card_ids` 至少一项出现在 **Top5** 且回答引用来源 ID」，所以：

| 参数 | 建议值 | 理由 |
|---|---|---|
| 检索匹配策略 | **语义检索** | 先跑基线；第二轮再对比「智能检索」（智能 = 语义 + 关键词综合排序） |
| **检索最大结果数** | **5** | 与评测集的 `top_k=5` 严格对齐，否则无法按验收规则判定 |
| 检索最小匹配度 | 0.500（默认） | 首轮用默认值，第二轮再扫 0.3 / 0.5 / 0.6 找最优 |
| 语义精排 | 先关闭 | 第二轮实验再对比（开启后：精排最大结果数默认 3、精排最小匹配度默认 0.800） |

## 四、上传后自检

用 `技能知识库/命中测试记录表.csv` 逐条核对（**54 条**，已只筛出本库可测的用例，结果列留空待填）：

1. 把 `query` 列逐条粘进平台「命中测试」，跑完把结果填进对应列；
2. 记录表列结构分两段，对应《效果评估报告框架》第 4.2 节的三项加严指标：

| 段 | 列 | 来源 |
|---|---|---|
| **检索层** | `检索_Top1文档` / `Top1匹配度` / `Top5期望项最高排名` / `Top5同源条数` / `命中@1` / `命中@5` | 平台「命中测试」直接读出 |
| **答案层** | `答案_引用等级是否正确` / `引用ID是否命中期望` / `Top1可回答性` | 让智能体真实作答后判定 |

**为什么要分两段测**：本方案一篇含 L1—L5 共 5 个等级，**检索单元是"技能"而不是"等级"**，所以"等级精度"在检索层根本测不出来——它只能在答案层看回答有没有引用对等级。这是方案B 带来的必然结果，也是报告里要写清的方法论细节。

全部 200 条用例的归属见 `命中测试对照表.csv`：另 **146 条**标注「本库是否覆盖 = 否」，指向学习资源（98）、岗位技能（29）、趋势解读（10）、隐私边界（9），需由其他知识库承接，**本次不测**——别把"没命中"当成本库的问题。

**必须自己加严的三项指标**（团队给的 acceptance_rule 只是 recall@5，两套方案都能通过，测不出优劣）：

| 指标 | 含义 |
|---|---|
| **技能精确命中率@1** | Top1 是否为期望技能文档，而非仅"在 Top5 里" |
| **同源冗余率** | Top5 里有几条来自同一技能（方案A 实测 5/5，冗余最重） |
| **Top1 可回答性** | 仅凭 Top1 内容能否回答该提问（方案A 的 Top1 仅约 60 字单句，答不了"等级1和等级2差在哪"） |

## 五、已知的数据侧问题（写进评估报告的"缺陷"章节）

| 问题 | 说明 |
|---|---|
| 等级文案模板化 | 同一技能的 L1≡L2、L3≡L4（去数字后一字不差），5 个等级只有 3 种文案。**这是必须向数据方反馈的原料缺陷**，本方案通过重组让它在文档中直接可见 |
| 通用评估句重复 | 「评估应引用近期课程、项目、测评或工作样例。」在每篇出现 5 次——300 张卡片 100% 相同。保真版保留原文；对照见下节 |
| `v0.5-core` 评测集失效 | 100 条用例有 48 条指向不存在的卡片（岗位匹配 0/15、趋势 0/5、隐私 0/4 全部无效）。已在反馈原文中定位到根因（`generate_dataset.mjs:1497` 的 `knowledgeCards.slice(0, config.knowledge)` 从头部截断） |
| 资源卡无技能外键 | 600 张 `learning_resource` 卡片的 `related_entity_type` 全为 `resource`，**无法聚合进技能文档**，必须由独立的学习资源库承接 |

## 六、对照版与可选扩展

**去模板版（A/B 实测用）**
`知识库构建/技能知识库_去模板版/` —— 同样 60 篇，剥离了那 5 处重复的通用评估句，篇幅 541—585 字。
生成命令：`python generate_skill_docs.py --strip-boilerplate`
用途：在同一条 query 上跑两组数字，验证「剥离模板噪音」是否真的提升区分度。**这是评估报告的核心实验之一。**

**未纳入的两类卡片（需你决策）**
`trend_interpretation`（60 张）与 `ethics_privacy`（60 张）**也是按技能关联的**（`related_entity_type = skill`），每个技能各 1 张。若把它们一并聚合进技能文档：

- 收益：本库可直测用例从 **54 条 → 73 条**（多覆盖趋势解读 10 条 + 隐私边界 9 条）
- 代价：每篇 **+约 135 字**，变成 781—825 字，**部分超过 800 字上限**；必须同时剥离通用评估句才能压回 676—720 字
- 另有一个需要权衡的点：文档会混入「趋势演示数据声明」「数据使用边界」两段合规文本，可能稀释"能力等级"这层的检索指向性

**当前默认不纳入。** 若你要，改脚本即可（这是设计决策，不是技术障碍）。

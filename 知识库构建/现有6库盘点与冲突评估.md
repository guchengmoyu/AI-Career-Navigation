## 二、字段级比对：现有库 vs v1.0-full 契约

### 2.1 岗位市场数据（70 行）

**现有字段**
```
job_id, job_title, industry, company_type, salary_range, experience_level,
education, skill_requirements, soft_skills, job_count, growth_rate, description
```
**应使用 `jobs.csv`（1500 行）字段**
```
job_id, role_id, title, company_code, industry, city, work_mode,
experience_level, required_experience_months, education_level, employment_type,
salary_min_cny_month, salary_max_cny_month, salary_is_simulated, summary,
posted_at, expires_at, display_disclaimer, schema_version, origin, is_synthetic,
source_ids, generated_at, confidence, claim_level, verification_status,
last_verified_at, license_scope, is_market_fact, data_split
```

**冲突点（严重）**
1. 缺 `salary_is_simulated` / `display_disclaimer` / `is_market_fact` / `claim_level` —— 这 4 个字段正是团队定的合规红线所需。旧表把 `25-45K·15薪`、`growth_rate=年增长35%` 作为**无标注的真实市场事实**呈现，直接触碰红线。
2. 缺 `role_id`，无法与 `roles` / `role_skills` / `career_paths` 打通。
3. 薪资是区间字符串 `salary_range`，无法计算；我们的契约是 `salary_min/max_cny_month` 数值。
4. 数据量 70 vs 1500。

### 2.2 教育资源数据（90 行）

**现有字段**
```
resource_id, resource_type, title, target_skill, difficulty, duration,
platform, description, career_stage
```
**应使用 `learning_resources.csv`（600 行）字段**
```
resource_id, resource_type, title, provider, url, difficulty, estimated_hours,
cost_type, language, prerequisite_score, verified_individual_page, page_kind,
metadata_scope, estimated_hours_is_simulated, summary, schema_version, origin,
is_synthetic, source_ids, generated_at, confidence, claim_level,
verification_status, last_verified_at, license_scope, is_market_fact, data_split
```

**冲突点（严重）**
1. 缺 `verified_individual_page` / `page_kind` / `metadata_scope` —— 这 3 个字段是区分「**官方已核验课程**」与「**公开目录话题卡**」的唯一依据。旧表把两类混在一张表里（如 `可汗学院·线性代数`、`Coursera·吴恩达机器学习`），**会违反团队已定的「`verified_course_metadata`(22条) 与 `public_catalog_topic_card`(98条) 严禁合并标注为官方课程」红线**。
2. 缺 `url` 字段，无法溯源到课程页面。
3. 缺 `prerequisite_score`，无法与技能分数体系挂钩。
4. 数据量 90 vs 600。

### 2.3 职业能力模型（80 行）

**现有字段**
```
model_id, job_title, capability_category, capability_name, weight,
target_level, assessment_method, description
```
**我们的技能知识库设计**
- 数据源：`knowledge_cards.csv` 的 `category=skill_level` 卡片 300 张
- 组织方式：**一技能一篇文档，60 篇**（已在 `知识库构建/技能知识库/` 生成完毕，646~690 字/篇）
- 检索目标：`retrieval_eval.csv` 200 条评测用例（围绕 `knowledge_cards` 的 `knowledge_card_id` 设计）

**冲突点（严重）**
1. **载体类型相悖**：旧库是「表格型」，按 `job_title × capability_name × weight` 组织；我们的方案是「文档型 + 一技能一篇」。评测集是按 `knowledge_card_id` 命中设计的，表格型无法承接。
2. 粒度错位：`capability_category/capability_name` 是**能力维度**（8 维雷达图那一层，对应 `dimensions` 表 8 行），不是 60 项原子技能（`skills` 表 / `knowledge_card` 粒度），两者不是同一层对象。
3. 缺 `skill_id` 外键，无法与 `role_skills` / `job_skills` / `user_skill_scores` 关联。

### 2.4 行业趋势报告（1 篇文档）

**冲突点**
1. 当前方案已定：**trend 不并入知识库**（原因：合规上 trend 必须标注演示数据；且评测集里 trend 相关用例仅 10/200，性价比低）。
2. 载体相悖：我们用的是 `trend_snapshots.csv`（720 行结构化时序快照），不是「报告文档」。
3. 另有 6 篇「行业趋势-*」游离文档仓库，同属该类别。

### 2.5 职场场景模拟（8 行）——超出职责边界

**现有字段**
```
scenario_id, scenario_name, category, role_setting, situation,
challenge_points, evaluation_criteria, expected_skills, difficulty
```
对应数据集 `scenario_cases.csv`（150 行），其 `module_owner = 对话/训练`。

**判定**：**不属于知识库职责**。知识库在 `data_dictionary` 中的归属是 `knowledge_cards`（知识库）与 `retrieval_eval`（评测）。场景模拟属于「对话/训练」模块，应由对话型应用直接消费该表，不必经知识库。且字段与契约完全不同（缺 `module_id/rubric_json/red_flags/privacy_focus/claim_level` 等）。

### 2.6 职业路径模板（33 行）——超出职责边界

**现有字段**
```
path_id, job_title, stage, milestone, key_tasks, estimated_time,
prerequisite, capability_gain, branch_options
```
对应数据集 `career_paths.csv`(24) + `career_milestones.csv`(120) 两张表，`module_owner = 路径`。

**判定**：**不属于知识库职责**，属「路径」模块。且把两张表压成一张，丢掉了 `path_id → milestone_id` 的层级关系与 `target_skill_id/target_score/acceptance_rule` 等可计算字段。

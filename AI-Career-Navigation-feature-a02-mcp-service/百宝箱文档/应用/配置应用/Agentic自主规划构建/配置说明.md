##### 提示词分层设计
一个清晰的系统提示词应该按**角色定义 → 行为规范 → 任务指令 → 约束边界**的层次组织。

###### 第一层：角色定义
用一句话明确智能体"是谁"，建立模型的自我认知。

```markdown
# 角色
你是 XX 公司的智能客服助手，专门处理用户关于订单、退款、物流的咨询。
你具备查询订单系统、发起退款流程、追踪物流状态的能力。
```

**要点：**

+ 明确身份（"你是……"）和能力边界（"你具备……的能力"）
+ 避免空泛描述（不要写"你是一个万能助手"），越具体模型表现越稳定

###### 第二层：行为规范
定义智能体的语气风格、交互原则和回复标准。

```markdown
# 行为规范
- 用专业但亲和的语气和用户交流，称呼用户为"您"
- 回复控制在 200 字以内，先给结论再给原因
- 涉及金额、订单号等关键信息时，必须从系统查询确认，不得凭记忆回答
- 遇到超出能力范围的问题，明确告知用户并引导转人工
```

###### 第三层：任务指令
描述智能体的核心工作流程，可以引用已配置的工具来明确执行路径。

```markdown
# 任务流程
1. 用户咨询订单问题时，先通过{订单查询插件}查询订单状态
2. 如果用户要求退款，使用{退款工作流}发起退款申请，将结果告知用户
3. 如果用户咨询物流，调用{物流追踪MCP}获取最新物流轨迹
4. 回复时使用{订单详情卡片}展示订单信息，提升阅读体验
```

###### 第四层：约束边界
划定模型不该做的事情，防止越界行为。

```markdown
# 约束
- 不得透露内部系统的接口地址、数据库结构等技术细节
- 不得替用户做出涉及资金的最终决策，必须让用户确认
- 不得编造不存在的优惠政策或承诺
- 用户要求的操作超出权限时，引导联系人工客服：400-xxx-xxxx
```

###### 常见问题
+ 需要写工具调用的格式吗？

**不需要。** 工具调用的格式协议（如 JSON Schema、参数说明）由平台自动注入到 System Prompt 的「工具调用协议」段落中。你只需在提示词中说明"什么场景用什么工具"即可。

+ 需要写当前时间、会话 ID 等环境信息吗？

**不需要。** 平台会自动注入环境上下文段落，包含当前时间、会话 ID、Agent ID、循环轮次等信息。

+ 需要写"你可以使用以下工具"这样的工具列表吗？

**不需要。** 平台会自动生成完整的工具描述列表并注入。你在提示词中引用 `{工具名}` 是为了明确业务流程，而非重复声明工具列表。

+ 提示词写得越长越好吗？

**不是。** 系统提示词应该简洁精准。冗长的提示词会占用模型的上下文窗口，挤压对话历史和工具结果的空间。建议控制在 500-1500 字以内。

+ 提示词中可以使用 Markdown 格式吗？

**可以且推荐。** 使用 `#` 标题分层、`-` 列表组织条目、代码块标记格式要求，能帮助模型更准确地理解结构化指令。

###### 工具描述配置
工具描述应包含以下要素：

```plain
[用途] 这个工具做什么
[场景] 什么时候应该用这个工具
[输出] 会返回什么结果
```

**示例：**

```plain
查询用户的订单详情，包括订单状态、商品列表、支付金额和物流信息。
当用户询问订单相关问题（如"我的订单到哪了"、"订单什么状态"）时使用。
返回订单的完整信息，包含订单号、状态、商品、金额和物流轨迹。
```

**写法对比：**

| 不推荐 | 推荐 |
| --- | --- |
| "查询订单" | "根据订单号查询订单详情，包含状态、商品、金额。用户问订单相关问题时调用" |
| "发送消息" | "向指定用户发送站内通知消息，支持文本和链接格式。需要用户确认后再发送" |
| "调用接口" | "查询指定城市未来3天天气预报，返回温度、天气状况和穿衣建议" |


###### 多个相似工具的区分
当智能体挂载多个功能相近的工具时，**必须在描述中明确使用边界**，否则模型容易混淆：

```plain
# 工具 A：query_order_by_id
根据订单号精确查询单个订单的详细信息。仅在用户提供了明确订单号时使用。

# 工具 B：search_orders_by_user
查询当前用户的订单列表（最近30天）。在用户没有提供订单号、想查看所有订单时使用。
```

###### 工具参数设置
每个插件工具的参数都可以配置**取值方式**，合理设置能显著提高调用成功率。

+ 参数取值方式

| 取值方式 | 说明 | 是否需要模型识别 |
| --- | --- | :---: |
| **模型识别** | 由模型从用户对话中理解并提取参数值 | 是 |
| **固定值** | 使用预设的固定值，每次调用都传相同的值 | 否 |
| **系统变量** | 引用运行时系统变量（如用户ID、会话ID等） | 否 |
| **默认为空** | 参数值固定为空，不传递 | 否 |


+ 配置策略

**核心原则**：能确定的参数尽量不让模型猜，只把真正需要从用户对话中理解的参数交给模型。

```plain
参数是否每次调用都一样？
  │
  ├─ 是 → 固定值（FIXED_VALUE）
  │       例：api_version="v2"、format="json"
  │
  └─ 否
      │
      ├─ 能从系统上下文获取吗？
      │    │
      │    ├─ 是 → 系统变量（SYSTEM_VARIABLE）
      │    │       例：user_id、tenant_id、conversation_id
      │    │
      │    └─ 否 → 需要从用户对话中理解
      │              │
      │              └─ 模型识别（LLM_GENERATE）
      │                  例：查询关键词、城市名、日期范围
      │
      └─ 参数可以不传？ → 默认为空（DEFAULT_EMPTY）
```

+ 配置示例

以"查询订单"工具为例，假设有 4 个参数：

| 参数名 | 取值方式 | 配置值 | 说明 |
| --- | --- | --- | --- |
| `order_id` | 模型识别 | — | 需要模型从用户对话中提取订单号 |
| `user_id` | 系统变量 | `$inputs.userId` | 从系统上下文自动获取，无需模型识别 |
| `api_version` | 固定值 | `v2` | 每次调用都用 v2 版本 |
| `extra_fields` | 默认为空 | — | 可选参数，默认不传 |


**效果**：模型只需关注从用户对话中提取 `order_id` 一个参数，其余 3 个参数由系统自动处理。参数越少，模型提取的准确率越高。

+ 模型识别参数的描述优化

对于需要模型识别的参数，参数描述的质量直接影响提取准确率：

| 不推荐 | 推荐 |
| --- | --- |
| `"id"` | `"订单编号，格式如 ORD20240101001，用户通常会说'订单号是xxx'"` |
| `"date"` | `"查询日期，格式 yyyy-MM-dd，如2024-01-15。不指定时默认查当天"` |
| `"city"` | `"城市名称，如'北京'、'上海'。支持中文城市名"` |


**描述要素：**

+ **含义**：参数代表什么
+ **格式**：期望的数据格式或示例
+ **默认值**：未提供时的默认行为
+ **约束**：合法值的范围或枚举

| "知识库1" | "售后退款政策" | 无语义，模型无法判断何时使用 |
| "数据" | "商品规格参数表" | 过于模糊 |
| "文档" | "员工入职手册" | 无法区分用途 |


+ 描述编写建议

描述应包含：**知识库里有什么内容** + **什么场景应该用它**。

| 不推荐 | 推荐 |
| --- | --- |
| "公司文档" | "包含公司组织架构、部门职责、联系方式。用户询问'xx部门负责什么'、'找谁对接'时检索" |
| "产品资料" | "包含所有在售商品的型号、参数、价格、库存。用户咨询商品信息、比较产品时检索" |


+ 多个知识库的区分

当智能体绑定多个知识库时，描述中必须明确各自的使用边界：

```plain
# 知识库 A：售后政策
包含退款条件、换货流程、保修期限等售后政策文档。
用户询问退款、换货、维修等售后问题时检索。

# 知识库 B：商品信息
包含所有在售商品的型号、参数、价格和库存。
用户咨询商品详情、比较产品、查询价格时检索。
```

如果描述不清晰，模型可能在用户问退款时误调用商品信息知识库，返回无关结果。

###### 不同类型知识库的召回差异
平台支持多种类型的知识库，不同类型在检索方式和参数能力上有显著差异：

+ 非结构化知识库（UNSTRUCTURED）

适用于文档型内容：PDF、Word、网页、Markdown 等文本文档。

**检索方式：** 基于用户问题进行语义检索或关键词检索，返回与问题最相关的文档片段。

**典型场景：** 政策文档检索、FAQ 问答、产品说明书查询。

+ 结构化知识库（STRUCTURED）

适用于表格型数据：Excel、CSV、数据库表等结构化数据。

**检索方式：** 除了语义/关键词检索外，还支持**字段过滤**和**排序**，模型可以构造精确的查询条件。

**字段信息自动注入：** 系统会从知识库的表结构定义中自动提取列名、列类型和列描述，生成字段过滤和排序的参数说明注入给模型。开发者在创建结构化知识库时，为每个列填写清晰的列名和描述，模型就能准确地构造过滤和排序条件。

**典型场景：** 商品数据查询（按价格筛选、按销量排序）、员工信息查询（按部门过滤）、订单数据分析。



##### 长期记忆配置
###### 什么是用户长期记忆
用户长期记忆是 自主的内置能力，它能**自动从每次对话中提取有价值的用户信息，并在后续对话中自动加载**，让智能体"记住"每个用户的偏好和历史。

```plain
第一次对话：
  用户："我对花粉过敏"
  → 系统自动提取记忆：[用户对花粉过敏]

第二次对话（隔天）：
  用户："明天杭州天气怎么样？"
  → 系统自动加载用户记忆，智能体知道用户对花粉过敏
  → 回复中主动提供花粉指数和防护建议
```

###### 对业务的价值
+ 个性化服务体验

智能体能记住每个用户的偏好、习惯和历史需求，无需用户重复说明：

| 记忆内容 | 业务场景 | 效果 |
| --- | --- | --- |
| 用户偏好的城市 | 天气查询 | 用户说"天气怎么样"自动查询常用城市 |
| 用户过敏信息 | 健康咨询 | 主动提醒花粉、饮食注意事项 |
| 用户常用联系人 | 订单查询 | 自动关联收件人信息 |
| 用户沟通风格偏好 | 全场景 | 记住用户喜欢简洁回复还是详细解释 |


+ 跨会话上下文连续性

传统对话在会话结束后丢失所有上下文。长期记忆让智能体跨越会话边界，保持对用户的持续了解：

    - **用户不需要每次重复背景信息**：首次告知后，后续对话自动关联
    - **服务质量随对话次数提升**：智能体越用越"懂"用户
    - **减少无效交互轮次**：不需要反复确认用户偏好
+ 用户粘性与满意度提升

在客服、导购、健康顾问等场景中，"被记住"的体验能显著提升用户的信任感和满意度，提高复访率。

##### 回复GUI交互卡片配置
###### 什么是交互卡片
交互卡片是智能体回复中嵌入的**可视化 GUI 组件**。与纯文本回复相比，卡片能以更直观的方式展示结构化信息，如商品列表、订单详情、天气预报等。

前端根据卡片 ID 匹配预制的卡片组件进行渲染，最终呈现为带有图片、按钮、标签等交互元素的富媒体内容。

<img src="https://cdn.nlark.com/yuque/0/2026/png/49692699/1780923453870-7b6fe4ca-1e63-44a8-8537-aeab3966d310.png" width="1062" title="" crop="0,0,1,1" id="u161ad044" class="ne-image">

###### 卡片在智能体中的决策流程
卡片的使用完全由模型自主决策，系统不会强制插入卡片。完整的决策流程如下：

```plain
用户提问
  │
  ├─ 1. 模型分析用户意图
  │     └─ 判断回答中是否有适合可视化展示的内容
  │
  ├─ 2. 匹配卡片
  │     └─ 模型根据每张卡片的「名称」和「描述」，判断是否有合适的卡片
  │         ├─ 有匹配的卡片 → 进入步骤 3
  │         └─ 无匹配的卡片 → 使用纯 Markdown 文本回复
  │
  ├─ 3. 填充卡片数据
  │     └─ 模型根据卡片的「数据 Schema」，将信息填入 JSON 格式的 data 属性
  │
  └─ 4. 组装回复
        └─ 模型将卡片标签嵌入 Markdown 正文中，前后搭配自然语言说明
            ├─ 开头：简要说明展示什么内容
            ├─ 中间：嵌入 <card> 标签
            └─ 结尾：总结或引导用户下一步操作
```

**关键点**：模型决定是否使用卡片的依据是卡片的**名称**和**描述**。如果名称和描述不清晰，模型可能在该用卡片的场景没有使用，或在不该用的场景误用。

---

###### 卡片名称和描述编写
+ 名称

名称应简洁明确，让模型一眼就能理解这是什么类型的卡片：

| 不推荐 | 推荐 | 原因 |
| --- | --- | --- |
| "卡片1" | "商品推荐卡片" | 无语义 vs 用途明确 |
| "展示" | "订单详情卡片" | 过于笼统 vs 限定具体内容 |
| "card" | "天气预报卡片" | 无法区分 vs 领域清晰 |


+ 描述

描述应包含两个要素：**卡片展示什么内容** + **什么场景下应该使用**。

**写法对比：**

| 不推荐 | 推荐 |
| --- | --- |
| "展示商品" | "以卡片形式展示商品列表，包含商品图片、标题、价格标签和租期信息。在用户搜索商品、要求推荐或比较产品时使用" |
| "订单信息" | "展示单个订单的详细信息，包含订单号、状态、商品、金额和物流进度。在用户查询特定订单详情时使用" |
| "显示数据" | "以图表形式展示数据分析结果，支持柱状图和折线图。在用户要求查看趋势、对比数据时使用" |


+ 多个卡片的区分

当智能体配置了多个卡片时，描述中必须明确各自的使用边界：

```plain
# 卡片 A：商品列表卡片
以网格布局展示多个商品的概要信息（图片+标题+价格）。
在用户搜索商品、浏览推荐、比较多个产品时使用。

# 卡片 B：商品详情卡片
展示单个商品的完整信息（规格参数+库存+评价+购买按钮）。
在用户点击某个商品、询问具体型号详情时使用。
```

###### 卡片参数配置
+ **字段名语义清晰**：使用 `productName` 而非 `pn`，模型更容易理解
+ **每个字段附带 description**：告诉模型这个字段应该填什么内容
+ **标明字段类型**：`string`、`number`、`boolean`、`array`、`object`
+ **标明必填字段**：通过 `required` 数组声明

### 常见问题
#### 自主规划构建的智能体能否调用其它子智能体？
可以调用，通过子智能体配置绑定需要调用的子智能体即可。

<img src="https://cdn.nlark.com/yuque/0/2026/png/49692699/1780923454374-127982aa-6dcd-4389-9bb8-5d8be6be41dd.png" width="462" title="" crop="0,0,1,1" id="ub7e7bd06" class="ne-image">

#### 子智能体回复的卡片能否在自主规划的智能体中展示呢？
可以展示，默认子智能体输出的卡片也会渲染。

#### 工作流搭建的智能体能否调用自主规划的智能体呢？
可以，通过工作流应用节点即可调用一个自主规划构建的子智能体，适合存量工作流构建的智能体针对部分业务模块通过自主规划来完成任务。
